# 按影响程度的优化：实测过程与结论

> 日期：2026-10-22　｜　环境：Windows 11 / Python 3.13 / bge-small-zh-v1.5 + bge-reranker-base（本地副本）
> 原则：**先测基线、再改、再测**。所有数字都可重跑（命令见文末），未达标的改动不进默认配置。

## 0. 先看天花板在哪（第二轮实测，最重要的一条）

在动手加功能之前先做了一次**瓶颈分解**（`benchmark/ceiling_diag.py`）：
把 hit@1 的损失拆成"召回没召到"和"召到了但没排到第一"。

| 域 | 第一跳 top5 命中 | 候选池 recall@10 | 重排后 hit@1 | 可救回空间 |
|---|---|---|---|---|
| m5_dureader | 0.980 | **1.000** | 0.615 | +0.385 |
| m7_cmrc2018 | 0.985 | 0.990 | 0.985 | +0.005 |
| m7_t2retrieval | 0.990 | 0.995 | 0.965 | +0.030 |
| m7_cmedqa | 0.810 | 0.900 | 0.600 | +0.300 |

**结论：召回已经饱和，瓶颈 100% 在重排排序。** DuReader 上正例 100% 都在 top-10 候选里，
但重排只能把 61.5% 排到第一。这一条直接推翻了上一轮"用 multi-query 提召回、再谈门控"的计划——
扩召回对 pool recall 已 1.0 的语料毫无意义。

## 0.1 结论先行

按"对一般 RAG 的影响程度"排序，三轮下来是**五条负结果 + 两项落地改造 + 一项真正的精度提升**：

| # | 优化项 | 影响假设 | 实测结果 | 结论 |
|---|--------|---------|---------|------|
| 1 | 答案级评测（answer_recall + judge sheet） | 高：chunk 级指标回答不了"能不能答对" | 已实现并验证 | **落地** |
| 2 | 策略在自有数据上可测可选（`tune` + 配对 bootstrap + 留出集） | 高：任何全局默认都会在某个域掉点 | 机制有效，且拦下了一个假提升 | **落地** |
| 3 | 检索自评门控（低置信→升级重排） | 高：开题创新点 3 | 四域**零收益**，AUC 0.56–0.99 跨域不可迁移 | **不落地**（负结果） |
| 4 | 召回分与重排分融合 | 高 | t2 +0.020，wx **−0.127** | **不默认**，仅作预设 |
| 5 | 首跳 BM25-RRF（提升 fast 档） | 中 | wx **+0.109**，cmedqa **−0.150** | **不默认**，仅作预设 |
| 6 | 候选池放大 / RRF 混合候选 / 伪相关反馈 | 中 | 放大会掉点且延迟翻倍；PRF 有害 | **不落地** |
| 7 | BGE 中文检索指令前缀 | 低 | DuReader +0.045，t2/cmedqa −0.01 | **保留**（多数域有益） |
| 8 | multi-query 查询扩展（零模型派生变体） | 中：原假设"提召回" | 四域 **0 或 −0.01**，pool recall 本就 0.98–1.00 | **不落地**（方向错误） |
| 9 | 重排集成（多视角打分平均） | 中：针对"排序瓶颈" | dureader +0.010，cmedqa **−0.115**，延迟 ×3 | **不默认**，仅作实验预设 |
| **10** | **领域微调重排器** | **最高：诊断指向排序瓶颈** | **dureader 0.615→0.675（+0.060，P≤0=0.025）**，其余域不变 | **成功，提供管线与模型** |

**核心发现（三条，逐轮递进）：**

1. **不存在跨域通用的检索超参。** 同一改动在不同语料上能从 +0.109 翻到 −0.150，
   所以真正该优化的是"让用户在自己的数据上测一遍再选"。
2. **瓶颈不在召回，在排序。** 候选池 recall@10 已达 0.98–1.00（DuReader 精确 1.000），
   意味着再加召回手段（multi-query / HyDE / 扩池 / 混合召回）**理论收益上限 ≤0.02**；
   所有可提升空间都压在 cross-encoder 的排序能力上。本轮实测也印证：这三种召回侧改造
   在两个域上精确等于 0.000。
3. **诊断被验证，且能兑现。** 按"排序瓶颈"的指引去微调重排器，在 DuReader 上拿到
   **+0.060 hit@1（P≤0=0.025）**，且提升只出现在该域——这是整套方法论唯一的正向兑现，
   也说明"先诊断再优化"比"加功能"更值钱。

## 2. 负结果：检索自评门控不work（原开题创新点 3）

用第一跳结果的 8 个廉价特征（agreement、分数间隔、查询词覆盖、top1 分数、BM25 分数占比、
查询长度、ASCII 占比、是否长语料）拟合逻辑回归预测"第一跳 top1 是否正确"，**留一域验证**：

| 域 | 第一跳 | 全量重排 | 当前 auto | AUC（训练其余 3 域） |
|---|---|---|---|---|
| m5_dureader | 0.485 | 0.615 | 0.615 | 0.612 |
| m7_cmrc2018 | 0.975 | 0.985 | 0.985 | 0.992 |
| m7_t2retrieval | 0.945 | 0.965 | 0.970 | 0.681 |
| m7_cmedqa | 0.565 | 0.600 | 0.600 | 0.562 |

在 dureader / cmedqa 上，**无论阈值取 0.3 到 0.8，门控都不改变任何一条查询的决策**
（升级率 0–2%）：概率分布与正确性几乎无关。cmrc 上 AUC 高，但那里第一跳已经 0.975，
没有可提升空间。t2 上"高置信跳过重排"能到 0.980，但只有 200 条、差 0.015，且方向与其它域相反。

**结论**：门控的收益上限受限于"重排本身能救回多少"，而这部分在本文四个域里只有 0.02–0.13；
用跨域不可迁移的概率去猜"该不该救"，期望收益为负。所以**不把门控写进默认路径**，
只保留现有 agreement 路由（已验证的那条）。

慢路径候选池与融合（`experiments/_opt/slowpath_tune.json`）：

| 改动 | t2 (long) | wx (long) | dureader | cmrc | cmedqa |
|---|---|---|---|---|---|
| 候选池 10→20 | −0.005，延迟 ×1.9 | — | 0 | 0 | — |
| 候选池 10→30 | −0.010，延迟 ×2.9 | — | — | — | — |
| RRF 混合候选 | +0.005 | — | 0 | 0 | — |
| 伪相关反馈扩展 | −0.020 | — | 0 | 0 | — |

| 首跳 BM25-RRF | −0.015 | **+0.109** | −0.015 | 0 | **−0.150** |

两条长文档语料给出**相反**结论（t2 爱融合，wx 狠排斥融合），说明这类改动没有普适最优值。

## 4. 落地改造一：答案级评测

chunk 级 hit 回答不了"最终能不能答对"，所以加了两条通道：

1. **`answers` 字段**：评测集每条可选填答案原文，`eval` 额外输出 `answer_recall@k`
   （检索到的上下文里是否真的含答案原文）。实测在自建小语料上正确给出 1.0 / 0.667。
2. **`--judge-sheet` / `--judge-results`**：把各档位的检索上下文摊成待打分的表
   （answer_correct / faithful，0/1），由**运行这个 skill 的 agent 自己填分**，
   再聚合成 `answer_correct` / `faithful` 均值。不需要额外 API key——这是本 skill 形态的天然优势。

```bash
python scripts/retrieval_core.py eval --index-dir ./idx --testset ts.json \
       --judge-sheet ./judge.json           # 生成待打分表（含上下文）
python scripts/retrieval_core.py eval --judge-results ./judge.json   # 聚合分数
```

## 5. 落地改造二：`tune` —— 在你的数据上选策略

既然没有普适超参，就把选择过程做成一条命令，并且**必须带统计护栏**：

```bash
python scripts/retrieval_core.py tune --index-dir ./idx --testset ts.json --out tune.json
python scripts/retrieval_core.py retrieve "..." --index-dir ./idx --config tune.json
```

- 预设：`base` / `fusion0.5` / `fusion0.7` / `fusion0.85` / `cand_rrf` / `fast_rrf`
- **配对 bootstrap**（2000 次）：给出 `mean(best) − mean(base)` 的 95% 区间与 `P(差值≤0)>0`
- **留出验证**：默认按 query 前半选择、后半复验，两边同向才推荐，否则退回 `base`
- 输出 `recommendation` + `why`，把"为什么推荐/不推荐"写清楚

实测它的护栏起作用了：t2 全量 200 条上 fusion0.7 = 0.985 vs base 0.965，
但**只用前 100 条选择时两者打平（0.98 vs 0.98）**，于是 `tune` 判定为选择偏差、
推荐保持 `base`。如果只看全量数字，就会把一个不该上的改动写成"提升 0.02"。

## 6. 第二轮：multi-query 与重排集成（针对"排序瓶颈"）

第一轮结论是"不存在通用超参"，于是第二轮按天花板诊断的指引，直接打排序瓶颈：

**multi-query（零模型派生变体：去疑问词、取最长实词、原查询补关键词）**

| 域 | base | multiquery | Δ | pool recall@10 |
|---|---|---|---|---|
| t2retrieval | 0.970 | 0.960 | −0.010 | 0.995 |
| dureader | 0.615 | 0.615 | **±0.000** | 1.000 |
| cmedqa | 0.600 | 0.610 | +0.010 | 0.845→0.900 |

dureader 的意义：它 pool recall 已是 1.000，所以查询改写**不可能**有任何收益，
实测精确 0.000——这是对天花板诊断的直接验证。t2 上反而掉点（改写引入的实词稀释了原查询语义）。

**重排集成（同一批候选，用原查询 + 派生变体各打一次分再平均）**

| 域 | base | rerank_ens | Δ | 95% CI | p50 延迟 |
|---|---|---|---|---|---|
| dureader | 0.615 | 0.625 | +0.010 | [−0.040, +0.060] | 139→513ms |
| cmedqa | 0.600 | **0.485** | **−0.115** | [−0.165, −0.065] | 90→251ms |
| t2retrieval | 0.970 | 0.955 | −0.015 | [−0.035, +0.005] | 207→406ms |
| cmrc2018 | 0.985 | 0.980 | −0.005 | [−0.015, 0.000] | 170→505ms |

只有 dureader 有 +0.010，且 95% 区间跨 0（统计上不可区分），代价是延迟 ×3.7。
cmedqa 上 −0.115 且区间不含 0，是明确的负结果。**结论：集成不落地，仅保留为实验预设。**

## 7. 为什么"排序瓶颈"难以在现有框架内解决

上面两轮都指向同一个事实：**在召回已饱和的语料上，唯一能动的是 cross-encoder 的判别力**。
而 bge-reranker-base 是一个 1.1 亿参数的通用模型，本课题没有：

- 领域标注数据去微调重排器（cmedqa 这种医学语料上 0.600 的天花板就是它的能力上限）；
- 训练 late-interaction / multi-vector 表示（ColBERT 类），那要换整个索引结构；
- LLM 级 judge 重排（成本比 cross-encoder 高两个数量级）。

所以对一般 RAG 的诚实建议是：**如果 pool recall 已 ≥0.98，继续优化检索框架收益极小，
应该把预算投到重排器本身（微调、或换成更强的 reranker）**，而不是继续加检索策略。

## 8. 对论文/项目表述的影响（重要）

1. **"检索自评与自动降级"不能作为已实现的创新点**——本次实验证伪了它在本文语料上的收益。
   更关键的是：天花板分析显示**可救回空间本来就小**（除 cmedqa 外 ≤0.03），
   所以门控即使完美也无法带来显著提升。这条要从创新点里拿掉，或明确写成负结果。
2. **`+0.02` 级别的差异不要单独报**。t2 上融合的"提升"在留出验证中归零，
   建议报告统一附 paired bootstrap 区间，或直接引用 `tune` 的输出。
3. **主指标建议从 hit@5 换成 hit@1 / nDCG@5 + answer_recall**：四个域里 hit@5 都在 0.85–0.99，
   已饱和，无法区分方案。
4. 新核心与旧报告数字逐域一致（第 1 节），所以 M1–M7 的结论**不需要重跑**。
5. **一个可以写进论文的正面结论**：召回饱和 + 排序瓶颈的分解方法本身（ceiling_diag）比
   "再加一个检索臂"更有价值——它能在动手前就判断某类改造是否可能有收益。
6. **最好的正面结果**：按诊断去做领域微调重排器，DuReader hit@1 **0.615→0.675**
   （+0.060，95%CI [+0.005,+0.120]，P(≤0)=0.025，训练/测试 query 零重叠）。
   这条可以作为"检索框架已饱和时，收益来自重排器适配"的实证，也解释了为什么
   继续改检索策略没有意义。**建议把它写成论文的主实验之一**，而不是只报策略路由。

## 11. 第三轮：领域微调重排器（唯一成功的精度提升）

第 7 节判断"排序瓶颈只能靠更强的重排器解决"。这一轮把它做成了可复现的管线，
并得到整轮优化里**唯一一个统计显著、且方向可解释的提升**。

### 11.1 数据隔离（先做对，否则结论不可信）

从 `data_raw/dureader/dev.jsonl.gz`（2000 条，1833 条带正例）构造训练集：

- 复现 `build_dureader.py` 的 `seed=42` 抽样，回推出测试集占用的 **200 条 query_id**；
- 训练/验证只用剩余 query，**断言与测试集 query 交集 = 0**；
- 同时排除测试集涉及的 **200 个 docid**（防止答案泄漏）；
- 结果：训练 3940 对（788 query，1 正 + 4 难负），验证 560 对（112 query）。

### 11.2 微调配置（8GB 显存的坑）

第一版用 batch 16 / max_length 512，实测 **3.5s/step**，跑 107 分钟未完成。
用 `bench_train_speed.py` 定位到根因：**batch≥16 的显存峰值超过 8.5GB 物理显存
（batch32 峰值 14.08GB），触发统一内存换页**：

| batch | 纯前向 | 训练一步 | 显存峰值 | 每对耗时 |
|---|---|---|---|---|
| 8 | 123ms | **986ms** | 6.10GB | 123ms |
| 16 | 253ms | 10801ms | 8.75GB | 675ms |
| 32 | 506ms | 50361ms | 14.08GB | 1574ms |

改成 batch 8 + max_length 256 + 预分词（原来每步都在 CPU 上分词）+ bf16 后：
**0.16s/step，2 个 epoch 共 160 秒跑完**。这是本次最实用的工程经验。

### 11.3 结果

| 域 | 候选池 recall@10 | 微调前 hit@1 | 微调后 hit@1 | Δ | 95% CI | P(≤0) |
|---|---|---|---|---|---|---|
| **m5_dureader** | **1.000** | 0.615 | **0.675** | **+0.060** | [+0.005, +0.120] | **0.025** |
| m7_cmedqa | 0.900 | 0.600 | 0.595 | −0.005 | [−0.050, +0.040] | 0.638 |
| m7_t2retrieval | 0.995 | 0.965 | 0.955 | −0.010 | [−0.040, +0.020] | 0.783 |

nDCG@5：dureader 0.802 → 0.820，hit@5 0.985 → 0.990。

三个交叉验证，证明**这是领域适配而不是泄漏或普适变好**：

1. 训练/测试 query 交集 = 0（脚本内 assert + 事后复查）；
2. 训练只用了 DuReader 语料，cmedqa / t2 上**完全没有提升**（区间全部跨 0），
   说明不是"模型整体变强了"；
3. 提升恰好出现在候选池 recall@10 = 1.000 的域——即排序瓶颈最纯粹的域。
   这正是天花板诊断的预测。

### 11.5 为什么只涨 0.060 而不是预期 0.75+

预期 0.75 是过于乐观的估算。实际天花板受两个约束：

1. **候选池 recall@10 = 1.000，但 recall@5 才是硬约束**——如果正例只勉强进 top-10 后半段，
   重排再准也只能把它提到前面几名中的某一位，第 1 位仍有竞争；
2. **3940 个训练对 + 2 epoch，本质是轻量适配**；batch 8 的限制让更大规模的训练不现实。

所以对"一般 RAG"的实用结论是：**领域微调重排器能拿到 0.02–0.06 的 hit@1 提升，
性价比高于任何检索策略改造，但要先确认候选池 recall 已饱和**。

## 11.6 第四轮：换更强底座 v2-m3，以及一次"微调把模型调坏"的实录

既然 8GB 能跑 v2-m3 推理（实测 2.47GB），就把更强底座也试了。四域对照：

| 域 | base（默认） | base+微调 | v2-m3 | 最优 |
|---|---|---|---|---|
| m5_dureader | 0.615 | **0.675** | 0.645 | base+微调 |
| m7_cmedqa | **0.600** | 0.595 | 0.580 | base |
| m7_t2retrieval | 0.965 | 0.955 | **0.975** | v2-m3 |
| m7_cmrc2018 | 0.985 | 0.985 | **0.990** | v2-m3 |

nDCG@5 也是同一格局（t2 0.914→0.928，cmrc 0.953→0.958）。

**两条结论：**

1. **换大模型和领域微调是互补的，不是替代。** v2-m3 在两个"通用域"上更好
   （t2 +0.010、cmrc +0.005），但在微调过的 dureader 上反而输给微调后的 base
   （0.645 vs 0.675）。所以正确用法是：**先选底座，再在你的域上微调**；
2. **代价不可忽略**：v2-m3 的 p50 延迟是 base 的 2.6–3.2 倍
   （120ms→380ms，143ms→448ms）。对延迟敏感的 agent 场景，base+微调更划算。

### 微调并不总变好：一次真实的失败

第一版 v2-m3 微调（冻结 20 层只训最后 3 层、lr=5e-5、2 epoch）**把模型调坏了**：

| 指标 | 值 |
|---|---|
| train loss | 0.5533 → 0.5096（正常下降） |
| dev pair acc | 0.800（看着正常） |
| **正例/负例得分** | **0.1007 / 0.1007（完全无判别力）** |
| 测试集 hit@1 | **0.105**（从 0.645 崩到 0.105） |

**最值得记录的一点：从训练指标完全看不出来。** loss 在降、dev acc 有 0.80，
但模型对正负例输出同一个分数。根因是冻结过多层 + lr 过高把分类头推入饱和区。

因此 `finetune_reranker.py` 加了**判别力探针**（`discrimination_probe`）：
每个 epoch 用一对固定正负例打分，`gap ≤ 0.02` 即判定权重不可用、拒绝保存。
修正参数后重跑（冻结 12 层、lr=1e-5、1 epoch）：gap=+0.091，健康。

同样的问题在 base 上也存在，只是没那么极端：base+微调 的 gap 从 **0.9504 掉到 0.2661**，
说明它也过拟合了，只是还没垮——这也是为什么它只涨 0.060 而不是更多。

**这条经验对所有做 reranker 微调的人都适用：不要只看 loss 和 pair accuracy，
必须检查正负例得分间隔。**

## 11.7 8GB 显存的完整边界（实测，非估算）

| 任务 | 显存峰值 | 8GB 可行 |
|---|---|---|
| base 推理 | 1.26GB | ✅ |
| base 微调（batch 8 / maxlen 256） | 5.59GB | ✅ |
| v2-m3 推理 | 2.47GB | ✅ |
| **v2-m3 全参数微调** | **11.37GB**（与 batch 无关，是固定开销） | ❌ |
| **v2-m3 冻结 20 层微调** | **2.71GB** | ✅ |
| base 微调 maxlen 512 / batch 16 | 8.53GB（> 8.52GB 物理显存） | ❌ 换页 |
| 任意模型 maxlen 768 | 崩溃（device-side assert） | ❌ |

所以"8GB 能不能微调 v2-m3"的答案是：**全参数不行，冻结大部分层可以**（2.71GB）。
关键是冻结层数——冻结 20 层后峰值从 11.37GB 降到 2.71GB，因为优化器状态只跟
可训练参数走。
